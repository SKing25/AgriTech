Propósito
El propósito de este proyecto es aplicar e integrar los conocimientos adquiridos durante
el curso de Ingeniería de Software, abordando las diferentes etapas del ciclo de vida del desarrollo de software. Esto comprende desde el levantamiento y análisis de requerimientos, la
identificación de actores y definición de roles, hasta el modelamiento de datos, diseño de la
arquitectura, implementación, pruebas y documentación del sistema.
La implementación consiste en desarrollar un sistema de información orientado a la agricultura de precisión, capaz de gestionar y monitorear las condiciones ambientales de un cultivo
mediante tres nodos IoT distribuidos estratégicamente en diferentes sectores del terreno. Cada
nodo contará con sensores de humedad y temperatura que permitirán recopilar información
en tiempo real sobre las condiciones del suelo y del entorno.
A partir de los datos obtenidos, el sistema realizará el procesamiento y análisis de la telemetría para generar reportes sobre el estado actual de cada sector agrícola. Adicionalmente, implementará mecanismos de automatización para activar los sistemas de riego mediante
electroválvulas cuando las condiciones de humedad lo requieran, considerando también la información meteorológica obtenida a través de una API externa, con el objetivo de optimizar
el consumo de agua y evitar riegos innecesarios.
Finalmente, el sistema permitirá consultar el estado meteorológico y generar alertas tempranas relacionadas con posibles condiciones ambientales desfavorables para el cultivo, proporcionando a los agricultores información útil para la toma de decisiones y la gestión eficiente de sus recursos.

Alcance
El proyecto se plantea como una propuesta experimental orientada al diseño e implementación de un sistema de información para la simulación de telemetría en un entorno agrícola. Inicialmente, el sistema contemplará la gestión de tres nodos sensores distribuidos en
diferentes sectores de un cultivo, encargados de recopilar y transmitir información sobre las
condiciones de humedad y temperatura.

1

La solución tendrá la capacidad de procesar y visualizar las mediciones obtenidas, gestionar los ciclos automatizados de riego y consultar información meteorológica mediante una
API externa. Asimismo, se contempla el diseño de una arquitectura escalable que permita
incorporar nuevos nodos, sensores y variables ambientales en función de los requerimientos
futuros del sistema.
Debido a su naturaleza experimental, la implementación estará enfocada en validar el funcionamiento, la integración y la interacción entre los diferentes componentes del sistema, sin
pretender constituir inicialmente una solución de producción para entornos agrícolas reales.

Restricciones de diseño e implementación
Las siguientes decisiones no son atributos de calidad del producto, sino restricciones impuestas por el curso y por el carácter experimental del proyecto:
10

RD-01. El prototipo se desplegará en una plataforma de computación en la nube (AWS,
GCP, Vercel o Render) accesible por Internet.
RD-02. La aplicación seguirá una arquitectura Modelo-Vista-Controlador (MVC) implementada con un framework web de Python (Flask, FastAPI o Django).
RD-03. Los tres nodos sensores y el servidor de electroválvulas se simularán por software como servicios independientes, que se comunicarán con el sistema a través de las
mismas interfaces que usarían los dispositivos reales (IE-02 e IE-03).
RD-04. La información se almacenará en una base de datos relacional.

Decisiones de delimitación
Tres roles de usuario. El sistema distingue al gestor de sensores, que opera el día a día; al
técnico agrícola, que aporta el criterio agronómico; y al administrador, responsable técnico de
la plataforma. Cada uno intercambia datos distintos con el sistema, por lo que se representan
como entidades separadas.
Dispositivos de campo como sistemas externos. El enunciado identifica a NodoSensorIoT y ServidorValvulas como entidades externas. Aunque en el prototipo se simulan, se
implementan como servicios independientes que usan las mismas interfaces que los dispositivos reales (IE-02 e IE-03). Así, reemplazar la simulación por hardware físico no modifica
la frontera ni la arquitectura del sistema (RNF-06).
La API meteorológica como servicio de terceros. La comunicación es de tipo solicitudrespuesta y siempre la inicia el sistema (F13), que recibe a cambio los datos meteorológicos
(F14). Estos datos alimentan la consulta del clima (RF-05), la decisión de posponer el riego
(RF-04) y las alertas tempranas (RF-06).

HU-01 — Encender y apagar nodos sensores (RF-02 | Must | 3 SP | Sprint S4 | EP01): Como gestor de sensores, quiero controlar el funcionamiento de los tres nodos sensores
(NODO-01, NODO-02, NODO-03) mediante opciones de encendido y apagado en la interfaz
gráfica, para iniciar o detener la captura y transmisión de telemetría en cada sector agrícola
según se requiera.
CA1. Dado un nodo sensor en estado apagado, cuando el gestor de sensores selecciona
la opción de encender en la interfaz web, entonces el sistema envía al NodoSensorIoT
la configuración de encendido y comienza a recibir sus lecturas de humedad y temperatura.
CA2. Dado un nodo sensor en estado encendido, cuando el gestor de sensores selecciona la opción de apagar en la interfaz web, entonces el sistema envía la configuración
de apagado y deja de procesar lecturas de ese sector.
CA3. Dado el panel de control de nodos, cuando el gestor de sensores cambia el estado
de cualquiera de los tres nodos, entonces la interfaz gráfica actualiza de forma inmediata
el indicador visual de estado (Encendido / Apagado).
CA4. Dado que todos los nodos sensores han sido apagados, cuando el sistema recibe
la señal de apagado, entonces el ciclo de monitoreo termina hasta que al menos un nodo
vuelva a encenderse.
HU-02 — Recibir y validar lecturas (RF-01 | Must | 5 SP | Sprint S4 | EP-02): Como
gestor de sensores, quiero que el sistema reciba y valide las lecturas de humedad y temperatura del suelo enviadas por cada nodo sensor encendido, para almacenar únicamente
mediciones válidas y descartar lecturas fuera de rango antes de actualizar el dashboard o
evaluar el riego.
CA1. Dado un NodoSensorIoT encendido que mide la humedad y la temperatura del
suelo, cuando envía la lectura al sistema con valores dentro del rango válido (humedad

lectura y la almacena con su fecha, hora y sector agrícola asociado.
CA2. Dada una lectura recibida desde un NodoSensorIoT, cuando presenta valores
fuera de rango físico o datos incompletos, entonces el sistema registra la lectura inválida, la descarta y no la utiliza para decisiones de riego ni alertas.
CA3. Dado un nodo sensor en estado apagado, cuando el sistema recibe una lectura de
ese nodo, entonces no la procesa ni la almacena.
CA4. Dada una lectura válida, cuando el sistema la procesa, entonces queda reflejada
en el dashboard en 2 segundos o menos (RNF-01).
HU-03 — Visualizar mediciones por sector (RF-01 | Must | 5 SP | Sprint S4 | EP-02):
Como gestor de sensores, quiero visualizar en una interfaz gráfica las mediciones actuales

temperatura (°C) actuales de cada uno de los tres sectores agrícolas junto con el estado

CA2. Dado un nuevo intervalo de muestreo con lecturas válidas, cuando el sistema

o menos (RNF-01).

móvil, cuando visualiza el panel de mediciones por sector, entonces la interfaz se adapta
a anchos de pantalla entre 360 y 1.920 píxeles sin desplazamiento horizontal (RNF-04).

HU-05 — Considerar el pronóstico antes de regar (RF-04, RF-05 | Must | 5 SP |
Sprint S5 | EP-03): Como gestor de sensores, quiero que el sistema consulte el pronóstico
del clima en la API meteorológica externa (APIMeteo) antes de activar las electroválvulas
cuando la humedad sea baja, para posponer el riego si se espera lluvia próxima y evitar
riegos innecesarios.
CA1. Dado un sector agrícola cuya humedad está por debajo del umbral mínimo, cuando el sistema evalúa la necesidad de riego, entonces consulta el pronóstico de las próximas 6 horas a APIMeteo antes de enviar el estado objetivo al ServidorValvulas.
CA2. Dado que el pronóstico de APIMeteo indica una probabilidad de lluvia mayor al
70 % y la humedad del suelo no es crítica (igual o superior a 15 %), cuando se evalúa
la decisión de riego, entonces el sistema pospone el riego y registra el motivo.
CA3. Dado que la humedad está bajo el umbral mínimo y la probabilidad de lluvia es
igual o inferior al 70 %, o la humedad es crítica (inferior a 15 %), cuando se evalúa el
pronóstico, entonces el sistema inicia el riego.
CA4. Dado que APIMeteo no responde en 5 segundos, cuando un sector presenta humedad inferior al umbral mínimo, entonces el sistema usa el último pronóstico válido

térmico.

de helada.

Diagrama de actividades
El diagrama de actividades de la Figura 6 describe el proceso de monitoreo y riego automático del sistema AgriTech Precision. Está organizado en cinco carriles: el gestor de sensores,
el sistema, los nodos sensores (NodoSensorIoT), el servidor de electroválvulas (ServidorValvulas) y la API meteorológica (APIMeteo).
Inicio y región interrumpible. El proceso inicia cuando el gestor enciende los nodos
sensores: el sistema envía la configuración de encendido y el nodo activa el muestreo. El
ciclo de monitoreo se modela dentro de una región interrumpible. Cuando el gestor apaga
los nodos, la acción de aceptación de evento Solicitud de apagado interrumpe la región, el
sistema envía la configuración de apagado, el nodo detiene el muestreo y la actividad termina
en el nodo final. De esta forma, el ciclo tiene una condición de parada explícita.
38

Lectura y validación. En cada intervalo de muestreo, modelado con el evento de tiempo
after(intervalo), donde el intervalo es el período de muestreo configurado para el nodo, el
nodo mide la humedad y la temperatura del suelo y envía la lectura. El sistema la valida: las
lecturas inválidas se registran y se descartan, y las válidas se almacenan. A partir de ese punto
el flujo se divide en dos ramas paralelas mediante una bifurcación (fork).
Rama de alertas. El sistema evalúa las condiciones de riesgo (fitosanitario, estrés térmico
y helada, según RF-06) y genera una alerta temprana si detecta alguna.
Rama de riego. El sistema compara la humedad con el umbral mínimo. Si está por debajo,
consulta el pronóstico a la API meteorológica; cuando la probabilidad de lluvia es mayor al
70 % y la humedad no es crítica, el riego se pospone. En caso contrario, el sistema envía el
estado objetivo abierta y el servidor abre la electroválvula. El seguimiento del riego se modela
en una segunda región interrumpible: en cada intervalo de muestreo el nodo envía una nueva
lectura y el sistema la valida y almacena, hasta que la humedad alcanza el objetivo. Si antes
se cumple el evento de tiempo after(45 min), este interrumpe la región y el sistema registra
el cierre por tiempo máximo y genera una alerta. En ambos casos el sistema envía el estado
objetivo cerrada, el servidor cierra la electroválvula y se registra el fin del ciclo de riego.
Unión y nuevo ciclo. Cuando ambas ramas terminan, la unión (join) sincroniza el flujo, el
sistema actualiza el estado del sector y el dashboard, y el proceso espera el siguiente intervalo
de muestreo hasta que se reciba la solicitud de apagado.
