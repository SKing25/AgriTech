Propósito
El propósito de este proyecto es aplicar e integrar los conocimientos adquiridos durante
el curso de Ingeniería de Software, abordando las diferentes etapas del ciclo de vida del desarrollo de software. Esto comprende desde el levantamiento y análisis de requerimientos, la
identificación de actores y definición de roles, hasta el modelamiento de datos, diseño de la
arquitectura, implementación, pruebas y documentación del sistema.
La implementación consiste en desarrollar un sistema de información orientado a la agricultura de precisión, capaz de gestionar y monitorear las condiciones ambientales de un cultivo
mediante tres nodos IoT distribuidos estratégicamente en diferentes sectores del terreno. Cada
nodo contará con sensores de humedad y temperatura que permitirán recopilar información
en tiempo real sobre las condiciones del suelo y del entorno.
A partir de los datos obtenidos, el sistema realizará el procesamiento y análisis de la telemetría para generar reportes sobre el estado actual de cada sector agrícola. Adicionalmente, implementará mecanismos de automatización para activar los sistemas de riego mediante
electroválvulas cuando las condiciones de humedad lo requieran, considerando también la información meteorológica obtenida a través de una API externa, con el objetivo de optimizar
el consumo de agua y evitar riegos innecesarios.
Finalmente, el sistema permitirá consultar el estado meteorológico y generar alertas tempranas relacionadas con posibles condiciones ambientales desfavorables para el cultivo, proporcionando a los agricultores información útil para la toma de decisiones y la gestión eficiente de sus recursos.

Alcance
El proyecto se plantea como una propuesta experimental orientada al diseño e implementación de un sistema de información para la simulación de telemetría en un entorno agrícola. Inicialmente, el sistema contemplará la gestión de tres nodos sensores distribuidos en
diferentes sectores de un cultivo, encargados de recopilar y transmitir información sobre las
condiciones de humedad y temperatura.

1

La solución tendrá la capacidad de procesar y visualizar las mediciones obtenidas, gestionar los ciclos automatizados de riego y consultar información meteorológica mediante una
API externa. Asimismo, se contempla el diseño de una arquitectura escalable que permita
incorporar nuevos nodos, sensores y variables ambientales en función de los requerimientos
futuros del sistema.
Debido a su naturaleza experimental, la implementación estará enfocada en validar el funcionamiento, la integración y la interacción entre los diferentes componentes del sistema, sin
pretender constituir inicialmente una solución de producción para entornos agrícolas reales.

Requerimientos funcionales
RF-01: El sistema debe permitir al usuario encargado visualizar las mediciones recopiladas por los nodos sensores mediante una interfaz gráfica intuitiva y legible, presentando
información como humedad y temperatura de cada sector agrícola.
RF-02: El sistema debe permitir al usuario encargado controlar el funcionamiento de los
nodos sensores mediante opciones de encendido y apagado disponibles en la interfaz gráfica.
RF-03: El sistema debe permitir generar y descargar informes en formato Excel (.xlsx)
que contengan los datos recopilados por los sensores, incluyendo sus respectivos valores,
fechas y sectores agrícolas asociados.
RF-04: El sistema debe evaluar automáticamente las mediciones de humedad del suelo
y temperatura del ambiente para ejecutar los ciclos de riego correspondientes mediante la
activación o desactivación de las electroválvulas, de acuerdo con los umbrales establecidos,
posponiendo el riego cuando el pronóstico indique lluvia y la humedad del suelo no sea crítica.
RF-05: El sistema debe permitir consultar las condiciones meteorológicas actuales y los
pronósticos del clima mediante la integración con una API externa, presentando la información obtenida en la interfaz gráfica, y debe generar alertas tempranas cuando se detecten condiciones desfavorables para el cultivo.

Requerimientos no funcionales
RNF-01: El sistema debe estar desplegado en un entorno de computación en la nube
que permita alojar y ejecutar aplicaciones web, garantizando su disponibilidad mediante una
conexión a internet.
RNF-02: El sistema debe estar desarrollado bajo una arquitectura MVC (Modelo-VistaControlador), utilizando un framework de desarrollo web como Flask, FastAPI o Django para
la gestión de rutas y endpoints.
RNF-03: La interfaz gráfica debe ser responsiva y adaptable a diferentes resoluciones de
pantalla, permitiendo su utilización desde computadores y dispositivos móviles.
RNF-04: El sistema debe garantizar el procesamiento y actualización de la información
recibida desde los nodos sensores en un tiempo adecuado, evitando retrasos significativos en
la visualización de las mediciones y la ejecución de los procesos automatizados.
RNF-05: La arquitectura del sistema debe permitir la incorporación de nuevos nodos sensores y variables ambientales sin requerir modificaciones significativas en la estructura general de la aplicación.

Decisiones de delimitación
Nodos y electroválvulas simulados, pero externos. El enunciado del caso identifica NodoSensorIoT, ServidorValvulas y APIMeteo como las entidades externas del sistema. El alcance del proyecto los simula por software con tres nodos, pero el sistema los trata como
terceros: recibe sus lecturas, les envía órdenes y consulta su estado a través de una interfaz
definida. Si en el futuro se incorporan nodos y válvulas físicos, solo cambiaría la implementación de esa interfaz y no el contexto del sistema, tal como lo plantea el RNF-05.
Un único tipo de usuario. Todos los requerimientos funcionales se dirigen a un mismo
usuario encargado, el gestor de sensores, que concentra la visualización, el control de los
nodos, la descarga de informes y la consulta meteorológica. Por eso el diagrama contempla
un solo actor humano.
Iniciativa de las interacciones. El gestor inicia sus solicitudes desde la interfaz. Los
nodos inician el envío de lecturas una vez encendidos. La comunicación con la API meteorológica y con el servidor de electroválvulas es de tipo solicitud-respuesta y la inicia siempre
el sistema. Los datos meteorológicos alimentan tanto la consulta del gestor (RF-05) como la
decisión de riego, que considera el pronóstico para evitar riegos innecesarios.

Especificación de las historias de usuario
A continuación se detallan las diez historias de usuario que conforman el Product Backlog
(HU-01 a HU-10), redactadas desde el rol del gestor de sensores junto con sus criterios de
aceptación y su trazabilidad con los requerimientos funcionales. Todas las historias comparten
la misma Definición de Terminado: código revisado e integrado en la rama main, pruebas
unitarias aprobadas, aplicación desplegada en la nube (RNF-01) y diagramas de actividades
y de secuencia actualizados.
HU-01 — Encender y apagar nodos sensores (RF-02 | Must | 3 SP | Sprint S4 | EP01): Como gestor de sensores, quiero controlar el funcionamiento de los tres nodos sensores
(NODO-01, NODO-02, NODO-03) mediante opciones de encendido y apagado en la interfaz
gráfica, para iniciar o detener la captura y transmisión de telemetría en cada sector agrícola
según se requiera.
CA1. Dado un nodo sensor en estado apagado, cuando el gestor de sensores selecciona
la opción de encender en la interfaz web, entonces el sistema cambia el estado del
NodoSensorIoT a activo y comienza a recibir sus lecturas de humedad y temperatura.
CA2. Dado un nodo sensor en estado encendido, cuando el gestor de sensores selecciona la opción de apagar en la interfaz web, entonces el sistema cambia el estado del
NodoSensorIoT a inactivo y detiene el muestreo de ese sector.
CA3. Dado el panel de control de nodos, cuando el gestor de sensores cambia el estado
de cualquiera de los tres nodos, entonces la interfaz gráfica actualiza de forma inmediata
el indicador visual de estado (Encendido / Apagado).
CA4. Dado que todos los nodos sensores han sido apagados, cuando finaliza el intervalo
de muestreo actual, entonces el ciclo de monitoreo se detiene hasta que al menos un
nodo vuelva a encenderse.
HU-02 — Recibir y validar lecturas (RF-01 | Must | 5 SP | Sprint S4 | EP-02): Como
gestor de sensores, quiero que el sistema reciba y valide las lecturas de humedad y temperatura del suelo enviadas por cada nodo sensor encendido, para almacenar únicamente

14

mediciones válidas y descartar lecturas fuera de rango antes de actualizar el dashboard o
evaluar el riego.
CA1. Dado un NodoSensorIoT encendido que mide la humedad y la temperatura del
suelo, cuando envía la lectura al sistema con valores dentro del rango válido (humedad
entre 0 % y 100 %, temperatura entre −10 ◦ C y 60 ◦ C), entonces el sistema valida la
lectura y la almacena con su fecha, hora y sector agrícola asociado.
CA2. Dada una lectura recibida desde un NodoSensorIoT, cuando presenta valores
fuera de rango físico o datos incompletos, entonces el sistema registra la lectura inválida, la descarta y no la utiliza para decisiones de riego ni alertas.
CA3. Dado un nodo sensor en estado apagado, cuando el sistema ejecuta el ciclo de
muestreo, entonces no procesa ni almacena nuevas lecturas de ese nodo.
HU-03 — Visualizar mediciones por sector (RF-01 | Must | 5 SP | Sprint S4 | EP02): Como gestor de sensores, quiero visualizar en una interfaz gráfica intuitiva y legible las
mediciones actuales de humedad y temperatura recopiladas por los nodos sensores en cada
sector agrícola, para conocer en tiempo real las condiciones ambientales del suelo.
CA1. Dado que existen lecturas válidas almacenadas, cuando el gestor de sensores consulta el dashboard en la interfaz web, entonces el sistema presenta la humedad ( %) y la
temperatura (◦ C) actuales de cada uno de los tres sectores agrícolas junto con el estado
de su nodo sensor.
CA2. Dado un nuevo intervalo de muestreo con lecturas válidas, cuando el sistema
actualiza el dashboard, entonces las mediciones en pantalla se refrescan sin retrasos
significativos (RNF-04).
CA3. Dado que el gestor de sensores accede desde un computador o dispositivo móvil,
cuando visualiza el panel de mediciones por sector, entonces la interfaz se adapta de
forma responsiva a la resolución de pantalla (RNF-03).
HU-04 — Activar riego automático (RF-04 | Must | 8 SP | Sprint S5 | EP-03): Como
gestor de sensores, quiero que el sistema abra la electroválvula cuando la humedad caiga
15

bajo el umbral mínimo y la cierre al alcanzar la humedad objetivo, para regar solo cuando
el cultivo lo necesita.
CA1. Dado un sector cuya humedad cae bajo el umbral mínimo, cuando se evalúa la
lectura, entonces se envía la orden de apertura al ServidorValvulas y se inicia el ciclo
de riego.
CA2. Dado un ciclo de riego activo, cuando la humedad alcanza el objetivo, entonces
se ordena el cierre de la válvula y se registra la duración del ciclo.
CA3. Dado un ciclo de riego activo, cuando pasan 45 minutos sin alcanzar el objetivo,
entonces la válvula se cierra por seguridad.
CA4. Dado un sector sin configuración propia, cuando se evalúa, entonces se usan los
umbrales por defecto (mínimo 30 %, objetivo 60 %).
HU-05 — Considerar el pronóstico antes de regar (RF-04, RF-05 | Must | 5 SP |
Sprint S5 | EP-03): Como gestor de sensores, quiero que el sistema consulte el pronóstico
del clima en la API meteorológica externa (APIMeteo) antes de activar las electroválvulas
cuando la humedad sea baja, para posponer el riego si se espera lluvia próxima y evitar
riegos innecesarios.
CA1. Dado un sector agrícola cuya humedad está por debajo del umbral mínimo (<
30 %), cuando el sistema evalúa la necesidad de riego, entonces consulta las condiciones y el pronóstico del clima a APIMeteo antes de enviar la orden de apertura al
ServidorValvulas.
CA2. Dado que el pronóstico de APIMeteo indica probabilidad de lluvia mayor al 70 %
y la humedad del suelo no es crítica (≥ 15 %), cuando se evalúa la decisión de riego,
entonces el sistema pospone el riego y registra el motivo.
CA3. Dado que la humedad está bajo el umbral mínimo y no se espera lluvia (≤ 70 %)
o la humedad es crítica (< 15 %), cuando se evalúa el pronóstico, entonces el sistema
envía la orden de apertura al ServidorValvulas.

16

CA4. Dado que APIMeteo no responde, cuando un sector presenta humedad inferior al
umbral mínimo, entonces el sistema ejecuta el riego con base en la lectura local de los
sensores.
HU-06 — Consultar el clima (RF-05 | Must | 3 SP | Sprint S5 | EP-04): Como gestor
de sensores, quiero consultar en la interfaz gráfica las condiciones meteorológicas actuales y
los pronósticos del clima obtenidos mediante la integración con la API externa (APIMeteo),
para contar con información meteorológica actualizada del cultivo.
CA1. Dado que el gestor de sensores solicita consultar el clima en la interfaz web,
cuando el sistema consulta a APIMeteo, entonces presenta en pantalla la temperatura
ambiental, humedad relativa y pronóstico de precipitación de la ubicación del cultivo.
CA2. Dada una respuesta exitosa de APIMeteo, cuando se renderiza en la interfaz gráfica, entonces se muestra la fecha y hora de la última actualización meteorológica.
CA3. Dado un fallo de comunicación con APIMeteo, cuando el gestor de sensores consulta el clima, entonces el sistema informa la indisponibilidad temporal del servicio
externo y muestra el último pronóstico registrado.
HU-07 — Recibir alertas tempranas (RF-05 | Should | 5 SP | Sprint S5 | EP-04): Como
gestor de sensores, quiero recibir alertas tempranas en el dashboard cuando el sistema detecte
condiciones ambientales o fitosanitarias desfavorables, para tomar decisiones oportunas y
prevenir afectaciones en el cultivo.
CA1. Dada una lectura válida almacenada y la información meteorológica del cultivo,

Diagrama de actividades
El diagrama de actividades de la Figura 6 describe el ciclo de monitoreo y riego automático
del sistema AgriTech Precision. Está organizado en cinco carriles: el gestor de sensores, el
sistema, los nodos sensores y el servidor de electroválvulas (estos dos simulados) y la API
meteorológica.
El proceso inicia cuando el gestor enciende los nodos sensores. Cada nodo mide la humedad y la temperatura del suelo y envía la lectura al sistema, que la valida. Las lecturas
inválidas se registran y se descartan, y las válidas se almacenan. A partir de ese punto el flujo
se divide en dos ramas paralelas.
En la primera rama, el sistema evalúa el riesgo fitosanitario, genera una alerta temprana
si detecta condiciones desfavorables y actualiza el dashboard, donde el gestor consulta las
mediciones y las alertas.
En la segunda rama, el sistema compara la humedad con el umbral mínimo. Si está por
debajo, consulta el pronóstico a la API meteorológica. Cuando se espera lluvia y la humedad
no es crítica, el riego se pospone. En caso contrario, se abre la electroválvula y se monitorea
la humedad hasta alcanzar el objetivo o cumplir 45 minutos. Después se cierra la válvula y se
25

registra el fin del ciclo de riego.
Cuando ambas ramas terminan, el sistema espera el siguiente intervalo de muestreo y
repite el ciclo mientras los nodos permanezcan encendidos.
